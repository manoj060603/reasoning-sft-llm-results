# Complete original solutions and three-epoch SFT

Frozen new candidate, October 17, 2026. Status: implemented for CPU verification; not yet submitted and no measured improvement. This candidate is distinct from the failed demonstration-response selector and does not relax its categories or reuse its generated answers for selection.

## Evidence and hypothesis

The demonstration-response candidate completed all 110,316 preparation requests, but found only 1,239 manageable and 2,978 currently missed examples against 6,000 required in each group (retention capacity 5,955). Its data were not exported, audit not run, and training not launched. Original logs and ledgers remain preserved. Its negative capacity result does not establish that the base model cannot learn any of the other examples: the two-draw prefix-response predicate was a proxy, not a gradient-learning experiment. Only 1,433 of 30K prompts had an incomplete/unsupported normal pair, so length censorship alone does not explain the large capacity shortfall. The selection hypothesis is retired unchanged.

The next test addresses **supervision coverage and exposure**. Recent recipes excluded all original solutions beyond 8K and used one prompt epoch. The assignment's reference recipe uses 16,384 tokens, three epochs, effective batch eight, learning rate 5e-6, cosine decay and zero warmup. See [the official assignment](https://github.com/reds-lab/Project-Reasoning-SFT-LLM). These are reference settings, not recovered settings of the historical winner.

[AceReason-Nemotron 1.1, section 4.4.3](https://arxiv.org/html/2506.13284v1) reports continued SFT improvements across epochs in its larger 7B setting. [Select2Reason](https://arxiv.org/html/2505.17266v1) finds response length informative and compares long-trace selection; it uses a different 7B model/dataset. These motivate testing complete longer original traces and repeated exposure. Neither establishes a 3B all-nine win, validates this exact selector, or implies that longer is always better. This is not a faithful reproduction of either entire paper and does not import their RL or inference changes.

## CPU pipeline audit corrections before any GPU submission

The new CPU audit inspected the **actual** LLaMA-Factory Alpaca converter, not only direct processor calls. Its default `DatasetAttr.system` is None; the prior SkillGraph `dataset_info.json` contained only a file name and converted the supplied system string to an empty `_system`, causing the template default system to be used. This is a concrete conditioning mismatch with the evaluator, not proof of the cause of prior score regressions. Earlier direct-row processor preflights did not test that mapping. The new dataset explicitly maps instruction/input/output/system and every selected row goes through the actual converter and `preprocess_dataset` before comparison of complete target labels, prompt masks and system identity. Its dataset-info digest is bound to the preparation receipt and checked again before training.

A separate CPU check initially rejected row 2170 because the pinned tokenizer canonically composed `y` plus combining macron into the equivalent single Unicode character. It contained the complete expected token labels and supervised EOS; it was not a cutoff loss. Exported source strings/hashes remain byte-for-byte unchanged. The decoded check now permits only canonical Unicode NFC equivalence in addition to exact byte equality, while still requiring equality of every actual supervised token with the full untruncated template encoding. Report the number of source responses requiring NFC composition. The synthetic CPU test includes this case. There is no generated replacement target, general whitespace cleanup or truncation waiver.
